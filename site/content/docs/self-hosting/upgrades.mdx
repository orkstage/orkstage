---
title: Upgrades and migrations
description: Upgrade a self-hosted OrkStage installation. Rebuild images, apply Prisma migrations with the migrate job, upgrade the OpenTofu runner and modules, and move instances to new template versions.
---

OrkStage has no tagged releases yet, so an upgrade means moving to a newer commit of the platform.
The procedure below is the one the Docker Compose stack uses.

## Platform upgrade

<Steps>
<Step>

### Back up Postgres

Take a database backup first (see [Backups and recovery](/docs/self-hosting/backups/)). Migrations
only move forward.

</Step>
<Step>

### Get the new code and rebuild

```bash
git pull
docker compose -f infra/local/docker-compose.yml --profile platform build
```

</Step>
<Step>

### Apply migrations and restart

```bash
docker compose -f infra/local/docker-compose.yml --profile platform --profile aws-emulator up -d --wait
```

The `migrate` service runs `prisma migrate deploy` (pending migrations only) and the idempotent seed,
then exits; `api`, `worker` and `web` start only after it succeeded. On a host install the same steps
are `pnpm db:deploy && pnpm db:seed`.

</Step>
</Steps>

Deployments in progress survive a worker restart: the job is re-delivered and resumes from its
persisted steps. Still, prefer upgrading when no deployment is running.

## Database migrations

Migrations live in `packages/database/prisma/migrations` and are generated by Prisma from
`schema.prisma` during development (`pnpm db:migrate`). The audit table's append-only trigger is part
of a migration; never edit it by hand.

## OpenTofu and modules

The runner image pins the OpenTofu version (`1.12.7`) and contains the modules. Upgrading them is an
explicit change of `TOFU_IMAGE` (or a rebuild of `orkstage/tofu-runner:local`). After the polyrepo
split, modules are versioned in `orkstage-modules` and the platform pins
`TOFU_IMAGE=ghcr.io/orkstage/tofu-runner:vX.Y.Z`, so infrastructure code changes are deliberate
upgrades.

Changing a module changes the plan of existing resources. The next deployment of each instance shows
it as the [provider plan](/docs/self-hosting/opentofu/#provider-plan-before-apply), and destructive
changes in production wait for approval.

## Template upgrades

Instances never move to a new template version by themselves. Publish the new version, then use
**Upgrade template** on each instance, review the plan and deploy.

## Compatibility

The template schema is versioned (`apiVersion: platform/v1`). API changes that break clients will
come with a new `/api/v2` route group. After the split, a compatibility matrix in `orkstage-dev`
lists the tested combination of platform, console, CLI and modules for each release.
