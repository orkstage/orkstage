title: OpenTofu runner and state
description: How OrkStage runs OpenTofu. Isolated throwaway runner containers, one state per resource in S3 with lockfile locking, no secrets in state, provider plans before apply, the approval escalation, drift scans and self-healing.
---

OrkStage provisions AWS with OpenTofu modules (`infra/tofu/modules/aws/*`, one per logical resource
type). The design is recorded in
[ADR 0005](/docs/contributing/architecture-decisions/#0005-opentofu-execution-and-state).

## The isolated runner

- The worker never runs IaC in-process. Every `tofu` command runs in a **throwaway container**
  (`ghcr.io/opentofu/opentofu:1.12.7`, pinned, or the `tofu-runner` image with the modules baked in).
- The module library is mounted read-only (or baked in); providers come from a shared plugin cache
  volume.
- Credentials are passed as environment variables **to that one container only**: never in files,
  command lines or state.
- Each command has a hard timeout (`TOFU_TIMEOUT_MINUTES`, default 45) and can be cancelled.

<Callout type="warn" title="Production follow-up">
  Today the worker starts runners through the Docker socket, which gives it control of the host's
  Docker daemon. Running the runner as an ECS RunTask or a Kubernetes Job with a scoped role is on the
  roadmap.
</Callout>

## One state per resource

State key: `orkstage/<physical-name>.tfstate`, not one state per instance or slot.

- Keeps the platform's own DAG, per-resource progress, retries and failure isolation.
- Limits the blast radius of a damaged state to one resource.
- Dependencies flow through module outputs passed as inputs; every module emits a `kind` output so
  the adapter wires them by type.
- The exact root configuration is stored next to the state (`.config.json`), so destroy never
  depends on a template that changed since.

**Backend**: S3 with `use_lockfile` locking and encryption. On real AWS the bucket is pre-provisioned,
versioned and encrypted, and validated before use (see
[Connecting an AWS account](/docs/self-hosting/connect-aws/#prepare-the-state-bucket)). On an emulator
it is created on first use.

## No secrets in state

RDS master passwords are generated with an OpenTofu `ephemeral` resource and written through
write-only attributes (`password_wo`, `secret_string_wo`). Services receive the Secrets Manager ARN as
an ECS secret. Verified: state holds `password: null`.

## Provider plan before apply

In the **Generate plan** phase, for every **existing** resource whose desired state changed, the
worker runs a real `tofu plan` and writes a summary per resource to the deployment's event log:

```text
INFO  [phase:plan] api: 0 to add, 1 to change, 0 to destroy
WARN  [phase:plan] ingress: 1 to add, 0 to change, 1 to destroy — replace aws_lb_target_group.route[0]
```

- Deletions and replacements make the deployment **high risk**. Routine ECS task definition revisions
  (a new image digest) do not.
- For a `production` instance, high risk **escalates** the deployment to `AWAITING_APPROVAL`, even
  when the platform's own diff only predicted an update.
- When nothing is destructive the approval step is marked skipped with the reason.
- The provider plans are stored on the deployment (`plan.providerPlans`) for review.

## Drift scans

Every `DRIFT_CHECK_INTERVAL_MINUTES` (default 360, `0` disables) the worker re-plans each applied
resource on real providers from the snapshot it was deployed with. Any planned action means a change
made outside OrkStage: the resource becomes `DRIFT_DETECTED`, an audit event is written and
`instance.drift_detected` is sent. Resources with pending changes are skipped. Redeploying restores
the template's configuration.

## Self-healing

When a resource is deleted outside OrkStage, its recorded state outlives it. The AWS adapter has a
**live existence probe**:

- during **verification**, a resource that is not healthy is probed; if it no longer exists the step
  fails immediately with "Resource no longer exists at the provider. Redeploy to re-create it." instead
  of waiting;
- verification uses **one 5-minute settle window per deployment**, not one per resource, so a slow
  service does not multiply the wait;
- on the **next deployment** the executor asks the provider whether converged resources still exist;
  missing ones are re-created instead of being skipped as unchanged.

## Verified against MiniStack

VPC, subnets and security groups, ECR, SQS with DLQ, S3, Secrets Manager, RDS Postgres (real
container), ElastiCache Valkey replication group (real container), ALB with target groups and listener
rules (live data plane at `/_alb/<name>/`), an ECS Fargate service (real container, registered in the
target group and healthy), Route 53 and ACM. The adapter contract suite passes against it.
