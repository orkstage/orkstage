## Tenants and organizations

An **organization** runs one OrkStage installation. It serves **tenants**: the customers or teams
that own instances. Every tenant-owned record carries its tenant id; users see a tenant only through
a membership with one of the [roles](/docs/user-guide/roles/). Each tenant is on a **plan**.

## Instance (stage)

An **instance**, also called a **stage**, is one isolated, logical environment: services, database,
cache, queue, storage, ingress and DNS for one tenant, for example *Acme Production* or *Acme
Staging*. It has an environment kind (`production`, `staging`, `development` or `sandbox`), a template
version, variable values and one placement binding per slot.

Instance status moves through a validated state machine:

```text
DRAFT → VALIDATING → PLANNING → [AWAITING_APPROVAL] → PROVISIONING → DEPLOYING
      → CONFIGURING → VERIFYING → READY | DEGRADED
failures: VALIDATION_FAILED · PLAN_FAILED · PROVISION_FAILED · DEPLOY_FAILED · VERIFICATION_FAILED
destroy:  DESTROYING → DESTROYED | DESTROY_FAILED
```

Only one operation runs per instance at a time; a second deploy or destroy gets `409 INSTANCE_BUSY`.

## Template

A **template** (`apiVersion: platform/v1`, `kind: EnvironmentTemplate`) describes business intent,
never provider resource blocks: "a container service with two replicas", "a zone-redundant Postgres",
"private connectivity from api to database". Templates are versioned; a published version is
immutable, and instances move to a new version only by an explicit upgrade. OrkStage ships six
built-in templates, from `free-validation` to `multicloud-reference`. See the
[template reference](/docs/developer/template-reference/).

## Placement slots and cloud targets

A **cloud target** is a registered account in a provider (an AWS account, an Azure subscription, an
OCI tenancy) with its allowed regions and non-secret configuration. Credentials are references, never
values.

A template declares **placement slots** such as `primary`, `data` and `storage`, each with the
providers it accepts. Every resource names a slot. An instance binds each slot to a target and a
region. Bind all slots to one AWS account and you get the single-cloud variant of the template; bind
`data` to Azure and the same template becomes multi-cloud. See
[ADR 0001](/docs/contributing/architecture-decisions/#0001-per-resource-placement-through-template-slots).

## Capabilities

Each provider adapter publishes a **capability catalog**: which concrete service implements each
logical resource type (`database.postgresql` → `rds-postgres` on AWS, `flexible-server` on Azure,
`oci-postgresql` on OCI), its features, regional gaps and static list prices. The resolver picks the
default or the `implementation` the template prefers, and suggests alternatives when nothing fits.

| Logical type | AWS (real) | Azure (simulated) | OCI (simulated) |
|---|---|---|---|
| `network` | VPC | Virtual Network | VCN |
| `compute.container-service` | ECS on Fargate, ECS on EC2 | Container Apps | Container Instances |
| `container-registry` | ECR | Container Registry | — |
| `database.postgresql` | RDS for PostgreSQL | PostgreSQL Flexible Server | Database with PostgreSQL |
| `cache.redis` | ElastiCache (Valkey) | Cache for Redis | — |
| `queue` | SQS | Service Bus | — |
| `object-storage` | S3 | Blob Storage | Object Storage |
| `ingress` | Application Load Balancer | Application Gateway | — |
| `dns` | Route 53 + ACM | Azure DNS | — |

## Plans and entitlements

A tenant's **plan** (`FREE`, `SANDBOX`, `STARTER`, `GROWTH`, `SCALE`) grants **entitlements**:
limits (instances, services, CPU, memory, storage, replicas, domains, retention) and switches (custom
templates, custom cloud accounts, multi-region, multi-cloud, autoscaling). A template lists the plans
it supports, and the compiler refuses a placement the plan does not allow, for example a second
provider without `multiCloud`.

| Plan | Instances | Multi-cloud | Multi-region | Custom templates |
|---|---|---|---|---|
| FREE | 1 | no | no | no |
| SANDBOX | 2 | no | no | no |
| STARTER | 3 | no | no | no |
| GROWTH | 10 | yes | no | yes |
| SCALE | 100 | yes | yes | yes |

These are the built-in defaults; the database copy is authoritative.

## Plan (deployment plan)

Previewing an instance compiles the template into a **resolved infrastructure**: variables applied,
each resource bound to a target, region and capability, names and tags assigned, a dependency graph,
a connectivity strategy per link, a policy report and an approximate cost. A diff against the known
resources gives the **deployment plan** (create, update, delete, unchanged) and its risk. Nothing in
this step touches a cloud, and a deployment stores the snapshot so what you previewed is what is
applied. See [Reviewing plan & cost](/docs/user-guide/plan-and-cost/).

## Deployment and the DAG

A **deployment** applies a plan asynchronously. The worker runs fixed phases (validate, targets, plan,
optional approval, resources, rollout, configure, verify, observability, finalize) and provisions
resources in dependency order, with independent branches in parallel. Transient failures are retried
with backoff; a failed resource skips only its dependents. A crashed worker resumes where it stopped.
See [Deploying and watching progress](/docs/user-guide/deploy/).

## Knowledge: desired, known, actual

The database holds **desired** state (template, configuration) and **known** state (what OrkStage
recorded). The provider holds **actual** state. Each resource carries a knowledge state (`DESIRED`,
`KNOWN`, `ACTUAL`, `UNKNOWN`) and a drift status.

## Health, incidents and status

Health (`HEALTHY`, `DEGRADED`, `UNHEALTHY`, `UNKNOWN`, `MAINTENANCE`) is checked per resource and
rolled up to the instance: a critical component that is unhealthy makes the instance unhealthy; any
other problem degrades it. Resources map to customer-facing **status components** (API, Workers,
Database, …) on a private **status page**. Alert rules open **incidents**, deduplicated per resource,
with a cooldown, resolved automatically when health returns. **Notifications** go in-app, by email and
to signed [webhooks](/docs/developer/webhooks/).

## Audit

Every state-changing action writes an **audit event**: actor (user or API key), tenant, resource,
action, correlation id and changes. The table is append-only, enforced by a Postgres trigger.
