Three endpoints exist for pipelines. Pipelines also use the regular deploy and deployment
endpoints.

| Method | Path | Scope | Body and result |
|---|---|---|---|
| `PUT` | `/api/v1/applications/:name` | `applications:write` | `{ displayName, repository, port, registryKind?, healthPath?, readinessPath? }` |
| `POST` | `/api/v1/applications/:name/versions` | `applications:write` | `{ version, imageUri, digest: "sha256:…", architectures? }` |
| `POST` | `/api/v1/templates/validate` | `templates:read` | `{ source, planCode? }`, returns a validation report |
| `POST` | `/api/v1/instances/:id/deploy` | `instances:deploy` | `{}`, returns `202` and a deployment summary |
| `GET` | `/api/v1/deployments/:id/events?after=` | `instances:read` | Progress events |

## Register the application

Every image version belongs to an application in the catalog. Create the application from the
pipeline before the first publish. The call is idempotent: the same body sent again changes nothing,
so you can run it on every build.

```bash
curl -fsS -X PUT "$ORK_API_URL/api/v1/applications/orders-api"   -H "Authorization: Bearer $ORK_TOKEN" -H "Content-Type: application/json"   -d '{ "displayName": "Orders API", "repository": "123456789012.dkr.ecr.us-east-1.amazonaws.com/orders-api", "port": 8080, "healthPath": "/health" }'
```

- A name has 2 to 63 characters: lowercase letters, digits and dashes, starting with a letter.
  Other names get `422 INVALID_NAME`.
- `registryKind` is `ecr` (the default), `acr`, `ocir`, `gar`, `dockerhub`, `ghcr` or `other`.
  `healthPath` defaults to `/health`.
- The response contains `"created": true` the first time. Every change is audited as `CREATE` or
  `UPDATE` on `Application`.
- The catalog is shared by all tenants, so the call needs an organization key with the
  `PlatformAdmin` role and the `applications:write` scope.

## Publish an image version

Templates refer to images through the application catalog (`image: catalog://orders-api`). When
OrkStage compiles an instance, each reference resolves to the **most recently published version** of
that application, by digest. A deployment therefore always runs an immutable image.

```bash
curl -fsS -X POST "$ORK_API_URL/api/v1/applications/orders-api/versions" \
  -H "Authorization: Bearer $ORK_TOKEN" -H "Content-Type: application/json" \
  -d '{
    "version": "1.14.2",
    "imageUri": "123456789012.dkr.ecr.us-east-1.amazonaws.com/orders-api:1.14.2",
    "digest": "sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
    "architectures": ["amd64", "arm64"]
  }'
```

- `digest` must be `sha256:` followed by 64 lowercase hex characters.
- `architectures` defaults to `["amd64"]`.
- Versions are immutable. Publishing a version again with the **same** digest is idempotent (the
  response has `"idempotent": true`). With a different digest it fails with `409 VERSION_EXISTS`.
- Every publish is audited as `PUBLISH` on `ApplicationVersion`.
- Publishing needs the same organization key as registration: role `PlatformAdmin`, scope
  `applications:write`.

## Validate a template in a pull request

The validation endpoint is stateless. It needs no template id and stores nothing.

```bash
jq -Rs '{source: ., planCode: "GROWTH"}' < .ork/template.yaml \
  | curl -fsS -X POST "$ORK_API_URL/api/v1/templates/validate" \
      -H "Authorization: Bearer $ORK_TOKEN" -H "Content-Type: application/json" -d @- \
  | tee report.json | jq -e '.valid'
```

The report lists every issue with its `stage`, `severity`, `code`, `message` and `path`.

## Deploy and wait

```bash
DEPLOYMENT=$(curl -fsS -X POST "$ORK_API_URL/api/v1/instances/$INSTANCE_ID/deploy" \
  -H "Authorization: Bearer $ORK_TOKEN" -H "Content-Type: application/json" -d '{}' | jq -r '.id')

while :; do
  STATUS=$(curl -fsS "$ORK_API_URL/api/v1/deployments/$DEPLOYMENT" -H "Authorization: Bearer $ORK_TOKEN" | jq -r '.status')
  case "$STATUS" in
    SUCCEEDED) echo "deployed"; break ;;
    FAILED|PARTIALLY_FAILED|CANCELLED) echo "deployment $STATUS"; exit 1 ;;
    AWAITING_APPROVAL) echo "waiting for approval in the console…" ;;
  esac
  sleep 5
done
```

If you deploy while another operation is running, the API answers `409 INSTANCE_BUSY`. Treat it as
"try again later", not as a failed build.

## GitHub Actions

<Tab value="curl">

```yaml title=".github/workflows/release.yml"
name: release
on:
  push:
    tags: ['v*']

jobs:
  publish-and-deploy:
    runs-on: ubuntu-latest
    env:
      ORK_API_URL: https://orkstage.example.com
      ORK_TOKEN: ${{ secrets.ORK_TOKEN }}   # organization key (PlatformAdmin): preset "CI/CD deploy" + applications:write
    steps:
      - uses: actions/checkout@v5
      # … build and push the image, capture its digest in steps.push.outputs.digest …
      - name: Publish the version to OrkStage
        run: |
          curl -fsS -X POST "$ORK_API_URL/api/v1/applications/orders-api/versions" \
            -H "Authorization: Bearer $ORK_TOKEN" -H "Content-Type: application/json" \
            -d "{\"version\":\"${GITHUB_REF_NAME#v}\",\"imageUri\":\"$IMAGE:${GITHUB_REF_NAME}\",\"digest\":\"${{ steps.push.outputs.digest }}\"}"
      - name: Deploy staging
        run: ./scripts/orkstage-deploy.sh "${{ vars.STAGING_INSTANCE_ID }}"
```

To keep publishing and deploying apart, use two keys: an organization key with the **Image
publishing** preset for the publish step, and a tenant key with the **CI/CD deploy** preset for the
deploy step.

## Notifications instead of polling

Subscribe a [webhook](/docs/developer/webhooks/) to `deployment.succeeded`, `deployment.failed` and
`deployment.awaiting_approval`. Your systems then react to the result without a job that keeps
polling.
